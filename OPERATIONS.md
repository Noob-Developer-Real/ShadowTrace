# Operate ShadowTrace

## Deployment

Start with a private staging environment. Use a supported PostgreSQL release with current patch updates. This release was verified against PostgreSQL 16.16. Use TLS at the service entry point and database TLS with `sslmode=verify-full` for TCP. A local Unix socket can be used when its ownership and permissions isolate it. Authorize the sole direct reverse proxy by address via `ST_TRUSTED_PROXY`; application ports stay private. Direct TLS is available through `ST_TLS_CERT` and `ST_TLS_KEY`. Set `ST_ORIGIN` to the exact HTTPS origin, with no path or trailing slash.

1. In a dedicated database, create two distinct login roles. Use a migration owner such as `shadowtrace_owner` and a restricted runtime role named `shadowtrace_app`. Both roles can be NOSUPERUSER, NOCREATEROLE, NOCREATEDB and NOBYPASSRLS. Make the migration owner the database owner. Do not grant the runtime role the owner group, schema creation rights, elevated extensions, or privileged role membership. Use generated SCRAM secrets or the deployment’s managed authentication. Restrict access to both roles with database and network policy.
2. Set `ST_OPERATOR_DATABASE_URL` for the migration owner in the secure operator environment. Run `uv run --locked --no-dev python -m shadowtrace.ops migrate` from this release directory. Apply a migration once as a controlled job. The ledger verifies checksums and runs changes inside a transaction.
3. Set `ST_OIDC_ISSUER` to the provider’s exact issuer. Register a confidential Authorization Code client supporting S256 PKCE and `client_secret_basic`. Register `https://<your-domain>/auth/callback` exactly. Enforce the required MFA and account recovery policy at the identity provider. The operator provisions users by issuer and stable subject, not by email domain.
4. Provision the workspace and admin with the operator environment:
   ```sh
   uv run --locked --no-dev python -m shadowtrace.ops workspace example "Example Company"
   uv run --locked --no-dev python -m shadowtrace.ops grant example "<verified-oidc-subject>" "Workspace Admin" admin
   ```
5. Build the immutable image with `docker build -t shadowtrace:0.0.0 .`. Configure runtime variables from [.env.example](.env.example) in your secret/platform manager. Use a cryptographically generated `ST_SESSION_SECRET` such as 48 random bytes encoded as URL-safe Base64. Supply the runtime database URL and IdP client credentials. Mount a private database trust bundle as needed. Start the non-root image on a private interface. Give the app a read-only root filesystem, drop capabilities, forbid privilege escalation and cap CPU/memory/concurrent connections at platform level. Deploy the same session secret across replicas.
6. Probe `/health/live` and `/health/ready` over the configured origin through the trusted proxy, or over direct TLS. Readiness checks database access without revealing DB internals. Run a test sign-in, admin/analyst permission check, an ingest and replay, a case review, and a cross-workspace denial before adding traffic. Verify SSO behavior against the actual provider.

The database stores hashes of integration key secrets and session tokens. The application’s DB connection runs with forced row policies on tenant data tables and scopes every protected request via a transaction-local tenant. The app role itself is a trusted backend principal. It relies on application authorization before selecting that tenant, and is not safe to give to an untrusted client. Never share runtime or operator DB credentials.

## Operations and recovery

- Schedule `python -m shadowtrace.ops purge` daily in the operator environment. It removes expired events, cases, reviews attached to expired cases, audit entries, sessions, OIDC requests and old rate-limit buckets and expired daily source health counters. Test retention with representative history. Events and audit are aged by receipt time, and cases by latest signal. Evidence links and view/export manifests expire with events. Destination receipts expire with their parent export, even when they arrived later. The operator can change retention using `python -m shadowtrace.ops retention <slug> <days>`. A lower retention is applied by the next purge.
- Use `python -m shadowtrace.ops revoke <slug> <subject>` for workspace access removal. This is effective at the next request. Separately disable compromised identities at the provider. Use distinct, revocable keys per source. Create a replacement with the same purpose, test delivery, then revoke the old key. New receipt IDs can use the replacement; a replay on another key returns a conflict. Keep connector HMAC secrets separate from delivery keys and follow [the token set rotation guidance](LINEAGE.md). Logs contain route templates, response statuses, durations and request IDs; configure proxy logging to omit credentials, query values and bodies.
- Monitor probe failures, 5xx and 429 rates, ingest latency, and database pool timeouts. Agree severity, escalation, and an operational owner before accepting customer data. During an incident, pause ingestion at the source, preserve relevant operator evidence, and rotate affected credentials. Apply workspace retention rules to backups as well as the live server.
- Configure encrypted database backups and recovery objectives at the chosen provider. For a single database exercise use `pg_dump --format=custom --enable-row-security --inserts --file=<protected archive> <operator-connection>`. To restore, create a clean staging database with the same migration-owner and restricted app roles, then use `pg_restore --exit-on-error --enable-row-security --no-owner --dbname=<staging-operator-connection> <protected archive>`. Use temporary credentials and private files. A logical backup also contains session hashes and temporary authorization state. Before putting a restored database into service, delete all rows from `st.sessions` and `st.oidc_state` with the operator role. Verify sample counts and tenant denial with the restricted role before routing traffic. For real workloads, pair this with the provider’s versioned backups and point-in-time restore.
- For upgrades, take a restorable snapshot, rehearse migration in staging, and retain the prior image and schema compatibility information. Shift a small portion of traffic first where your platform supports it. Roll back the image only when its schema is compatible. After incompatible changes, use the tested snapshot restoration path. Capture application and database version, RPO, RTO, and operator notes.
- Use a separate demo or staging instance for synthetic traffic. Production config requires HTTPS, a configured OIDC provider and restricted database access. It rejects the demo login route. The product collects pseudonymous access metadata and user-entered review notes. Determine disclosure, accepted retention, and data-subject procedures before connecting a real customer application.

## Upgrade from 1.4

Take a protected backup and apply migration 006 before starting the service. It adds managed links, transfer approvals and optional limits. Existing protection policies default to zero for the new rules. The migration creates ordinary indexes. Rehearse and schedule an appropriate window if your decisions table is large. Set `ST_SHARE_S3_BUCKET` only after configuring the private versioned bucket and a restricted workload identity. See [MANAGED-TRANSFERS.md](MANAGED-TRANSFERS.md). Pause 1.5 connectors and managed link distribution before rolling back to an earlier application version.

## Upgrade from 1.3

Take a protected backup and apply migration 005 before the upgrade. Existing audit and receipt data stay in place. The migration adds protection policy and decision tables and a new credential purpose. A production workspace defaults to paused until it saves a policy. Add protection enforcement to source routes only after validating the staged deployment and the fail-closed path in [PROTECTION.md](PROTECTION.md). Protection decisions follow the workspace retention policy. If the policy API becomes unavailable, integrated source routes withhold new transfers until service is restored.

## Upgrade from 1.2

Take a protected backup. Run the operator migration job before starting 1.3. Migration 004 preserves earlier receipts as unsigned and leaves prior event manifests intact. It adds the signature, deadline, impact and saved-view schema. It creates ordinary indexes on existing tables. Schedule a maintenance window and rehearse on a representative copy if those tables are large. See [RESPONSE.md](RESPONSE.md) for connector rollout. If a rollback to 1.2 becomes necessary, pause 1.3 connectors first. They send new payload fields and depend on 1.3 policy semantics. Retain the migrated database for a forward fix or restore the protected backup according to your recovery policy.

## Upgrade from 1.1

Take a protected backup and apply migration 003 with the migration owner before starting 1.2. It adds separate receipt credentials and two new tenant-scoped tables. Existing keys remain event keys. Existing cases and count-only events are preserved and old event payloads remain replayable. Deploy receipt-capable connectors after the app is ready. If rolling back the app to 1.1, stop receipt delivery first; keep the additive schema and lineage data for the next upgrade. Perform representative staging load checks for high event volumes and source counts.

## Upgrade from 1.0

Take a protected backup, run `python -m shadowtrace.ops migrate` as the migration owner, and make sure all migrations for the release are recorded before starting it. Apply migration 002 in a maintenance window on large event tables because it adds regular indexes. Existing reviews retain their decisions without a close reason. Existing cases start unassigned. Source health counters begin with 1.1 deliveries. Last accepted receipt uses retained events, including older ones. The browser demo launcher runs the migration automatically against its own local database.

Rule replay is capped per run. For capacity planning, test the added source counter updates and actor-history reads with your tenant distribution. Review and download audit entries follow workspace retention. A case's owner is cleared when that owner loses membership.
