# ShadowTrace 1.3 workflows

Scope agreed in chat: signed destination receipts, source-side customer impact resolution, then a follow-up queue. Use the approved light workspace, existing controls and inline feedback. The editable screen outlines below define the order and behavior of the added controls. Existing cases, unsigned receipts and count-only exports continue to work.

## ST13-01 · Signed destination receipts

**Settings / Integration / Create key** (workspace admin): key label → purpose → a destination alias and raw Ed25519 public key when registering a signed receipt source → Create key → copy bearer secret once → Done. Leave both signing fields blank for a legacy receipt source. A registered key requires signed deliveries for its alias. Rotate by creating a new credential and revoking the old one. An analyst can view proof in Record lineage but cannot create or revoke credentials.

**Record lineage** (workspace member): export summary → Destination receipts → proof label → Receipt details → receipt ID, accepted time and reported digests. States: Same file, Different file, Signature verified / source digest unavailable, Unsigned receipt, and no receipt. A verified signature identifies the registered signer of the claim. Both sides calculate SHA-256 over the exact bytes they handled. The receiver signs the normalized receipt, manifest digest, workspace slug and file digest. The API authenticates the bearer, verifies its binding and signature, stores immutable receipt and proof with the export, and returns only the delivery acknowledgement. Exact retry returns the same acknowledgement. Invalid signature, missing signature on a bound key, wrong alias, stale timestamp and mismatched idempotency payloads fail without a saved receipt.

## ST13-02 · Customer impact

**Record lineage / Customer impact**: linked customer case → select scope and reason → enter a reference → Request lookup → show request ID, state and expiry. Any workspace member may request. A workspace admin other than the requester may approve. The requester or an admin can cancel a pending or approved request. The approval control shows only when eligible. Connector failures leave the request visible for retry until expiry. The customer integration pulls the approved job with a source-bound impact credential, resolves exactly the supplied fingerprint snapshot in a local catalog, saves a private local results file and reports the count. The browser shows counts, requester, ticket, reason and state. Raw IDs and results stay at the source. Expired requests cannot be approved or fulfilled. A cancellation cannot reclaim a snapshot already delivered; the connector must stop if completion is refused. No email or webhooks.

## ST13-03 · Follow-up queue

**Cases → Follow-up**: reason and review-state filters, My cases, Apply, Clear, Save filters → queue items with reason labels, export link, case status and owner, receipt deadline and back navigation. Empty state explains monitored exports. Query filters are shareable. Save filters retains one personal view per workspace. An item needs review until a linked case is closed with a review entered after the newest material change. A late first qualifying receipt, a verified unexpected alias, a file digest mismatch and extra signed records on a full manifest count as material changes. An overdue deadline applies until the expected signed destination reports a qualifying receipt. Exact replays do not create findings. A closed case can be reopened via its review form. The server versions linked cases when important receipt evidence arrives so a stale review is rejected. Exports without a case offer Open a case in Record lineage. A repeated request returns the existing case.

| Field ID | Control, limits and persistence |
|---|---|
| key.purpose | Required select for admins, Audit events by default. Also supports Destination receipts and Customer impact. Stored immutably on the credential. |
| key.destination, key.signing_public_key | Optional pair for receipt keys. Alias 1–80 ASCII ID characters and 64 lowercase hex characters representing the 32-byte raw public key. Error requests both values. Immutable on creation. |
| key.source_key_id | Required source credential for impact keys. Admin selects an active event source. Server checks capability and workspace. Stored as a composite reference. |
| export.artifact_sha256 | Optional SHA-256 (64 lowercase hex characters) on a successful manifested export. Immutable and saved alongside the manifest. |
| export.expected_destination, export.receipt_due_minutes | Optional expected alias. Deadline defaults to 60 minutes from export acceptance, with a 1–10,080 minute override. Server requires an expected alias for a deadline override. |
| receipt.artifact_sha256, receipt.signature | Required together for signed receipts. SHA-256 and 128 lowercase hexadecimal characters. Validated before saving. Export comparison and manifest hash are derived server-side. |
| impact.scope | Required select, Export manifest or Same-file receipt matches. Server snapshots only deduplicated export fingerprints. |
| impact.reason, impact.ticket | Required reason select (incident scoping, customer notification, remediation) and opaque ticket ID (1–80 ASCII ID characters). Stored with request, shown in case trace and audited. |
| impact.id, impact.matched_count | Server idempotency UUID used for approval and source lookup. Connector reports an integer bounded by the original snapshot, with repeated identical completion accepted. |
| followup.reason, followup.state, followup.owner | Workspace-specific filters, default All reasons / Needs review / All owners. Stored on explicit Save filters per member and restored at unfiltered entry. |

Acceptance: forged and cross-tenant writes fail; identical record overlap with different bytes remains visible; unsigned receipts never qualify for a signed deadline; lookup requires separated approval and correct source key and expires; no fingerprint snapshot in browser; late and unexpected receipts resurface a reviewed case without changing its decision; mobile, keyboard, dark appearance and inline feedback work; existing database upgrades additively.
