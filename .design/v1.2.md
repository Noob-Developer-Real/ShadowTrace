# ShadowTrace 1.2 · Record lineage

The approved light workspace and static evidence patterns apply. This extends the case and activity journeys. The user's prior direction to deliver the working product governs this iteration. This document records the workflow before implementation.

- **FLW-10, analyst.** Case → Record lineage → select an export → read the overlap summary, source activity and destination receipts. Activity also links directly from any successful export, including those below alert thresholds. Copies of trace links require workspace membership. The page distinguishes count-only exports, partial fingerprint coverage, no receipts and complete receipt coverage of supplied fingerprints. It explains that integration observations have a limited remit. Case downloads include bounded snapshots of export traces without raw fingerprints.
- **FLW-11, integration admin.** Settings → Integration → Create key → select Audit events or Destination receipts. Server enforces the capability. The admin gives each application its own key and provisions the same workspace fingerprint secret and token-set identifier at authorized sources. Send read/export manifests through the extended endpoint and separately send receipts referring to a specific export. Last accepted time and delivery health include receipt sources. Rotation revokes a key through the existing workflow.
- **FLW-12, presenter.** Overview → Run record lineage demo → inspect the case and export trace. The fixture submits three real API events and a destination receipt with separate credentials. It shows 570 exported, 520 previously viewed, 410 destination matches, 390 of those present in all stages, and 160 exported fingerprints with no receipt match. Demo sources are clearly synthetic.

| Field ID | Type, validation, use |
|---|---|
| FLD-key-purpose | Admin select. Optional API field defaulting to Audit events for older integrations. Values events or receipts. Required in new UI. Persists on key creation and cannot be changed. |
| FLD-token-set | UUID, required in manifest and receipt. Sources sharing a workspace secret and normalizer use the same identifier. Export receipt must match parent token set. |
| FLD-fingerprints | Array of 1–1,000 distinct lowercase HMAC-SHA256 hex values. A manifest is optional on successful events, bounded by the reported record count. Receipts contain a bounded set for one instrumented operation. Source-side HMAC key and raw record identifiers stay with the source. |
| FLD-export-id | Existing event ID, required on a receipt. Must identify a successful export in the authenticated workspace with a manifest. Return generic 404 for missing, foreign or unsuitable parents. |
| FLD-receipt-id | Identifier matching the event identifier rules. Reuse on retry. Existing ID and same normalized payload returns replay. Changed content yields 409. |
| FLD-destination | 1–80 character opaque destination alias, limited to existing identifier alphabet. Use a registered source-side alias and avoid personal data. |
| FLD-receipt-time | RFC 3339 with explicit offset. Use the independently observed destination time. Validate same delivery window as other events and no prior occurrence relative to parent export. |
| FLD-review-trace | URL export selector comes from saved workspace event. Workspace asserted first, then direct event lookup. |

The analysis records prior successful views for the same actor, resource and token set over seven days by reported occurrence time, with at most 500 matching view manifests, and up to 50 source-reported receipts per export. It uses set intersections and union so repeat sightings cannot inflate counts. Separate key capability and source labels identify reporters. Values absent from the supplied export manifest are labeled outside that manifest. They may belong to the same export if source coverage was partial. No claim of uninstru­mented travel or inferred transfer path. Use an ordered trace with counts, timestamps, coverage and provenance instead of a node-link graph that implies unobserved edges.

The existing theme tokens apply to the trace. A narrow layout stacks its stages and wraps identifiers. Semantic lists and text labels carry all count information. A download retains the existing permission check and audit record. Server validation controls body size, token format and count, lookup scope, idempotency, and receipt rate. Database row policy and composite foreign keys provide additional isolation. Fingerprints and receipts expire with the parent event. Cases with older count-only events will explain coverage. Reproduction checks include known intersections, partial manifests, multiple overlapping receipts, outside-manifest values, denial across keys and workspaces, legacy replay, retention, demo and responsive browser rendering.
