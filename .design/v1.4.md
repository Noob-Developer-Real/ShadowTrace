# ShadowTrace 1.4 · Protection workflow

Approved product direction in chat: extend investigation to active protection. Keep the light workspace, inline save feedback and static evidence. The following editable screen outline defines this incremental workflow.

**ST14-01 · Configure protection.** Workspace admin → Protection → Export, Download and Share limits → destination allowlist → set Active or Paused → Save policy → inline status and current revision. An analyst can read the policy and decisions. A workspace starts paused with an empty allowlist. Administrators can pause releases immediately for subsequent checks. Concurrent policy changes reject stale forms. A rotated protection credential continues to use the current policy. Existing audit, receipt and resolver credentials cannot authorize releases.

**ST14-02 · Enforce at source.** The connected app first authenticates and authorizes the user, resolves the destination server-side and prepares a frozen transfer privately. It supplies the actor alias, action, resource type, record count, destination alias, request UUID and SHA-256 via a server-side credential. ShadowTrace resolves the workspace from the credential, evaluates the current locked policy and commits an immutable verdict. A first valid response can authorize exactly one attempted release through the shipped connector callback. A deny, transport failure, invalid response or repeated authorization ID leaves the callback untouched. The source owns its operation ID, routes and payload, and must require the check on each protected path. The policy does not recall operations that already obtained a decision.

**ST14-03 · Verify and investigate.** Protection → Run protection demo → sample export to the configured approved destination and sample share to a personal destination → compare results. Demo invokes the actual authorization endpoint and a source-local release callback, with synthetic bytes only. Recent decisions show action, actor, resource, metadata, reason, revision and source. Filter by action or verdict, navigate pages, and clear. An allowed decision records authorization, even if delivery later fails. Destination receipts remain the evidence of reported delivery.

| Field | Control and persistence |
|---|---|
| policy.mode | Active or Paused. Default Paused. Server authoritative. |
| policy.export_limit, download_limit, share_limit | Integers 0–1,000,000. 0 disables the action. Allow up to and including the limit. |
| policy.destinations | Unique ASCII aliases, up to 20, 1–80 characters each. Workspace admin supplies them, connectors resolve them from trusted routing. Active requires at least one. |
| policy.version | Read-only current revision in UI, required on write. Reject stale revision with a reload message. |
| authorization.request_id | Source-owned UUID, unique across its workspace. Existing ID produces no authorization. |
| authorization.actor_id, destination | Opaque ASCII identifiers, 1–80 chars; tenant derived from credential. Never send customer emails or URLs. |
| authorization.action, resource_type | Export/download/share, and customer/order/invoice. |
| authorization.record_count, content_sha256 | Positive integer up to one million; hash of exact staged bytes or serialized change, lowercase SHA-256 hex. |
| log.outcome, log.action | Optional filters on a permission-scoped paginated list. Default all. |

Acceptance: actual source release callback runs once on an allowed operation and never on a denied, replayed, stale/error or wrong-credential operation; policy change is audited and compared to server version; workspace isolation and failed CSRF checked; mobile and keyboard usable; existing database upgrades additively.
